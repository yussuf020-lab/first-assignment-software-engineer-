Exercise A: Explaining the SDLC
Prompt 1 — Zero-Shot
Prompt used:
Explain the Software Development Life Cycle.
Output:
The Software Development Life Cycle (SDLC) is the structured process teams follow to plan, build, and maintain software. It generally breaks down into seven stages: Planning, Requirement Analysis, Design, Development, Testing, Deployment, and Maintenance.
Planning is where a team defines scope, sets goals, and checks whether the project is even feasible. Requirement Analysis follows, gathering and documenting what the software actually needs to do — usually through stakeholder interviews. Design turns those requirements into a technical blueprint: architecture, database structure, UI, and how everything fits together. Development is the coding stage, where engineers build what was designed. Testing catches bugs and confirms the software behaves as expected before anyone outside the team sees it. Deployment pushes the product live, and Maintenance keeps it running — fixing issues, releasing updates, and adapting to new needs over time.
Different organizations move through these phases differently (Waterfall runs them in sequence, Agile cycles through them repeatedly), but the core phases stay largely the same no matter which model is used.
Summary (3–5 sentences):
This plain-language prompt returned a clean, accurate overview of the SDLC's seven phases, written at a neutral technical level. It reads like a solid reference entry — correct and complete, but generic, with no sense of who it's for or how it should be applied. There's no formatting to speak of and nothing tailored to a particular reader. It's a reasonable starting point, but it would need follow-up prompting to become genuinely useful for a specific task or audience.
Prompt 2 — Role Prompting
Prompt used:
You are a senior software engineering instructor preparing training material for complete beginners who have never worked in tech before. Explain the Software Development Life Cycle (SDLC) in a way a non-technical audience can understand. Format your answer as a table with three columns: Phase, What Happens, and a Real-World Analogy (e.g., comparing it to building a house).
Output:
Phase	What Happens	Real-World Analogy
Planning	Decide what problem the software will solve, estimate cost and time, and confirm the project is worth pursuing.	Deciding you want a house and working out your budget and timeline before calling anyone.
Requirement Analysis	Talk to future users to understand exactly what the software needs to do.	Sitting down with an architect to describe how many rooms you want and what each one is for.
Design	Sketch out how the software will be built — screens, data, and how the pieces connect.	The architect draws detailed blueprints covering wiring, plumbing, and layout.
Development	Engineers write the code that brings the design to life.	Construction crews build the house according to those blueprints.
Testing	Check for bugs and confirm the software does what it's meant to.	A home inspector checks the wiring, plumbing, and structure are sound.
Deployment	Release the finished software so real users can start using it.	Moving in and actually living in the house.
Maintenance	Fix problems, make improvements, and keep things updated.	Ongoing upkeep — repairing a leaky roof, repainting, renovating a room.
Just like building a house, skipping a step — proper planning, a thorough inspection — tends to cause expensive problems later. That's the whole point of the SDLC: it exists to reduce risk and make sure what gets built actually matches what people needed.
Summary (3–5 sentences):
Giving the AI a role, a named audience, and a specific format changed the output considerably. The house-building analogy makes an otherwise abstract process feel concrete and relatable to someone with zero technical background, and the table format turns it into something scannable and easy to reuse — as a handout or slide, for instance, rather than a wall of text. It's a good illustration of how the exact same underlying knowledge can be reshaped almost entirely by who it's for and what it's meant to be used for.
Comparison
●Which response was more useful? It depends on the goal. For training a beginner, the role-based version wins by a wide margin — it's more digestible and immediately usable. For a quick technical refresher, the zero-shot version is arguably faster to read and just as accurate.
●What did I change? I added a role ("senior software engineering instructor"), named the audience (complete beginners), and specified an exact output format (a table with an analogy column).
●How did the role and audience affect the response? The role nudged the tone from "reciting facts" toward "teaching." Naming the audience forced the AI to swap jargon for everyday language and lean on analogies instead of technical definitions. The format requirement did the rest — it organized the same information into something that's genuinely easier to reference later.
